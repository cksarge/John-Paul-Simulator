# Tutorial Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An offline guided course that teaches every core system in about 6 minutes, offered once on first launch and always available from Play.

**Architecture:** The tutorial is a Training Range variant. The mode `tutorial` uses `kind: 'training'`, so it gets the sandbox for free: an endless live phase, buying always allowed, no recording and no stats, challenges or achievements. `game.js` creates a `Tutorial` (new `js/game/tutorial.js`) instead of `Training` when `mode.id === 'tutorial'`. The runner holds an ordered list of steps. Each frame it polls game state (player position and flags, world props, `state.bomb`, HUD overlay) to decide whether the current step is done, so the rest of the game needs almost no hooks.

**Tech Stack:** Plain ES modules, three.js, no build step. Served with `python3 -m http.server 8765`.

**Spec:** `docs/superpowers/specs/2026-11-13-tutorial-design.md`

> **Deviation from spec:** the spec says `kind: 'tutorial'`. This plan uses `kind: 'training'` with `id: 'tutorial'` instead, because every sandbox rule (`canBuy`, `Rules.startTraining`, no stats or achievements, no recorder) already keys off that kind. `this.training` stays `null` in the tutorial, so the drill UI never appears.

## Global Constraints
- No database writes, stats, achievements or XP for the tutorial.
- The `course` map has `training: true`, so it never appears in `playMaps()`, the bot-match map picker, the workshop or any rotation.
- Every key hint uses `pad.label(action)`, or a `keyHint` helper with the same keyboard/controller split, so controller players see button names.
- localStorage keys are `jps_tutorial_seen` (the first-launch card was answered) and `jps_tutorial_done` (the course was finished). Every read and write is wrapped in try/catch, like the rest of the codebase.
- Copy: the first-launch card says "New here? Play the tutorial (about 6 min)" with **Play** and **Skip**. The end screen says "Tutorial complete" with **Play vs bots**, **Training Range** and **Menu**.
- Match the surrounding code style: dense, terse comments, single-quoted strings, 2-space indent.

## Review Focus
1. **Dying mid-course** (fall from the catwalk, own frag): you respawn at the current step's checkpoint, not the map spawn, and the step doesn't reset to step 1.
2. **A controller player**: every prompt shows button names, and every step can be finished on a pad (the buy menu is opened with D-pad ←).
3. **Pressing Escape or leaving the tab mid-step**: the pause menu shows Skip step and Leave tutorial, and resuming continues the same step.
4. **Doing a step out of order** (e.g. reloading before the reload step): earlier actions don't auto-complete later steps. Checks only count events after the step starts, using the baselines captured in `enter()`.
5. **Leaving and replaying**: starting the tutorial again begins at step 1 with a clean world, with doors closed, the gate shut and the cracked wall intact.

Each one is pinned to a check in the task that owns it.

- Produces:
  - `export class Tutorial { constructor(game); update(dt); onKill(killer, victim); skip(); get index(); get step(); dispose() }`
  - `export const STEPS` (array). Each step is `{ id, title, help: (k) => string, zone, enter?(tut), done(tut) => bool }`. `k` is the key-hint helper `keyHint(action)`, which returns `pad.label` where it exists and otherwise a keyboard/pad pair from a local table (move, jump, crouch, walk, reload, inspect, nade, ping, emote, scores).
  - `tut.base`: a snapshot object `enter()` fills, so `done()` compares against the step's start (Review Focus 4).
  - `g.tutorial` is set on the game. `g.training` stays `null`.

**Steps 1–6** (each `zone` places the floor ring and beam marker; `done` as listed):
1. `look`: the camera yaw has moved more than 1.5 rad in total since `enter`.
2. `move`: the player is inside `walk`. `walk-key`: has walked (`p.walking`) for 1 s.
3. `jump`: standing on top of the `jump` crate (`p.onGround` and `p.pos.y > 0.9` inside `jump`). `crouch`: `p.crouching` while inside `crouch`.
4. `mantle`: `p.mantle` was seen, then the player is on the ledge. `ladder`: in `ladderTop` after `p.climbing` was seen. `lift`: in `liftBottom` having started in `ladderTop`.
5. `door`: the `D` prop in `door` is `.open`. `gate`: the `P` prop is `.open`.
6. `shoot`: three dummy kills (spawned in `range` with the `Training` dummy look and placement code; reuse it by importing `DUMMY_LOOK` and moving the shared `place` logic into an exported helper in `training.js`). `reload`: `p.ws.reloadT >= 0` was seen after `enter`. `switch`: the slot went secondary, then melee, then primary. `inspect`: the viewmodel inspect started.

On completing a step: `sfx` success tick, a short `hud.center('✓', title, 1)`, then the next step. Each step also has `section` (1–9, matching the spec's course sections). The objective panel shows `Step <section>/9 · title` and `help(k)`, and re-renders when `pad.active` changes.

**Checkpoint respawn (Review Focus 1):** on local death, respawn after 1.2 s at the current step's `zone` centre (the previous zone if the current one is unsafe, e.g. `liftBottom`), with the step state kept.
